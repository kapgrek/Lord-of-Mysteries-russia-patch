## Как устроен перевод StringDB (для понимания всех пунктов)
- `bootstrap.lua:411-419` (`merge_overlay`): для каждой строки таблицы вызывается `Loader.TranslateDatabaseString(value, origCn, key, name)`. `value` — английский текст оверлея CPDD, `origCn` — китайский оригинал игры.
- `Init.lua:10909-10952`: row-оверрайды → поиск в шардах по **CN** (точный + `lookupGeminiTextFuzzy`) → по **EN** → `visibleTextExactOverrides` → промах (`Diag.OnDbMiss`).
- Шард — побайтовый ключ (`Init.lua:2042-2079`, FNV-1a). `lookupGeminiTextFuzzy` (`Init.lua:2091-…`) обрезает пробелы **у входной строки**, снимает внешний тег, хвостовую пунктуацию и скобки. Регистр не нормализуется.
- Ключи шардов пишет `tools/ShardCompiler.cs:65-104`: `source_cn → ru` и `ref_en → ru` (для EN побеждает первый батч, кроме `batch_028`), плюс жёсткий словарь `explicitAliases` (`ShardCompiler.cs:108-340`).
- **Промахи StringDB — это не «что видел игрок».** Диагностика пишет промах для каждой строки оверлея при загрузке модуля (все пять сессий дают 8135–8718 строк независимо от маршрута). На экране в виджетах за шесть папок логов подтверждено только **119** из них.
- У 18 «разделённых» модулей (`_buffdata`, `_gossip`, `_talkother`, `_item*`, `_skill*` и др., 2201 строка) `cn` пустой: `originals[key]` = nil. Для них перевод возможен **только по EN-ключу**.

## Первопричина

### 1. Записи боёв Автошахмат: в батчах нет строк одного уровня
- Энциклопедия показывает **сводную** строку всех уровней, записи боёв — **строку одного уровня**, и это разные строки StringDB:
  - энциклопедия: `batch_028_autochess:131439` «…total value of 12/18/26 Gold Coins…, including at least 1 3/4/5-cost piece» → переведена;
  - записи боёв: `StringDB_CN_Data` row `158675419318528`, cn «随机获得总价值<HighLight>12金币</>的棋子，至少包含<HighLight>1个3费棋子</>。», en «…total value of 12 Gold Coins<HighLight></>, including at least 1 3-cost piece<HighLight></>.» → ни CN, ни EN в шардах нет;
  - row `158469797713664` «罪恶廷根棋子获得<HighLight>15%</>攻击…» — в батчах нет ни одной строки с «罪恶廷根棋子» и «总价值» (поиск по `source/translation_batches` — 0 совпадений).
- `batch_028` собирали по видимому тексту энциклопедии: в 462 из 633 записей `source_cn` содержит английский текст (EN-ключ), китайских строк StringDB там нет.
- **Почему инструменты не помогли:** `tools/StringExtractor.cs/.ps1` читает не StringDB, а **уже существующие шарды** `RuntimeTextGemini_*.lua` (`StringExtractor.cs:19-45`) и **перезаписывает** `batch_001…` с нуля (`StringExtractor.cs:61-84`, путь `d:\gameDev\AbsoluteRU` зашит, в конце копирует себя из чужой папки `.gemini`). Новые строки из StringDB им не добавить, а запуск уничтожит батчи. `BatchHelper.ps1` адресует файл как `batch_{N:D3}.json` (`BatchHelper.ps1:124,153,231`), поэтому к `batch_028_autochess.json` и `batch_029_cpdd_264.json` обратиться не может. Готового способа «выгрузить промахи StringDB в батч» нет — единственный похожий код в `SyncCpdd.ps1:363-387` (новые строки CPDD → `batch_0NN_cpdd_*.json`).
- **Объём Автошахмат** (эвристика по ключевым словам `棋子|弈|共鸣|金币|羁绊|棋|阵容` / `piece|Resonance|Gold Coin|lineup|Chess`): **378** строк (таланты и аугменты 149, резонансы 83, интерфейс 114, «вопрос — ответ» справки 32). Ещё **215** строк — формулы урона фигур с макросами `{*d,F1690001,atkMin,1.62}` (row `158333969…`, `159431601…`, рядом с диапазоном талантов), вероятно, подсказки фигур Автошахмат. В TASK-010 оценка была ~283.

### 5. Системная порча перевода: хвост строки заменён на `b`
- В **4460** записях (`batch_006`…`batch_027`, по 150–280 на батч; `batch_001–005`, `028`, `029` чисты) последние 1–2 символа `target_ru` заменены на `b`/`bb`: `第17天` → «День bb», `每周日 19:30` → «Каждое воскресенье 19:bb», `副本50` → «Подземелье bb», `永久限购00` → «Постоянный лимит покупки bb», `9级` → «Уровень b» (`batch_022:105846`), «…Adventure Storb» (`batch_014:066644`), «Бонус Willpower_Percentagb». У 4188 из них `ref_en` оканчивается цифрой, у 269 — латиницей.
- Внесено коммитом `dfcfd7f` («merge 101k high-quality strings from master translation», 2026-09-13): в `dfcfd7f^` те же id корректны (`batch_006:025130` «…фракции 4»). **1644** записи отличаются от `dfcfd7f^` только хвостом — восстанавливаются дословно. **2816** получили в `dfcfd7f` новую формулировку — у них хвост восстанавливается по цифрам из `ref_en`/`source_cn` (k букв `b` = последние k символов недостающей группы цифр), неоднозначные — вручную.
- Многие из них служебные, но есть видимые: даты и время, «День N» ежедневных наград, лимиты магазина, уровни.
